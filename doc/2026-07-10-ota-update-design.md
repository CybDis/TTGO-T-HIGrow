# OTA Updates via Home Assistant `/local` (Pull-OTA)

Design: 2026-07-10
Implemented: Release 5.4.0, 2026-07-11

## Goal

The TTGO T-HiGrow sensors receive new firmware without a USB cable. The
firmware is hosted locally on Home Assistant (no internet hosting). Since the
devices spend almost all their time in deep sleep, each sensor checks for a
new version itself on wake-up (pull principle).

## Decisions

- **Trigger:** Check on every wake-up (hourly, every 5 min in charging mode).
- **Rollout:** One shared firmware for all sensors. Device-specific data
  (plant name, soil calibration, battery info) lives in SPIFFS and survives
  the update.
- **Position in the cycle:** Right after the WiFi connect, **before** NTP,
  measurement and MQTT. On update the device flashes and reboots immediately;
  measurement and publish are done by the new firmware. A new version is live
  without a 1-hour delay and tests don't drag on.
- **Version comparison:** Manifest version ≠ own `rel` ⇒ update. Deliberately
  "different" instead of "greater", so putting an older version back into the
  manifest rolls devices back (downgrade support).
- **Deployment:** Automated via PlatformIO target (`pio run -t ota_deploy`).

## Implementation

### 1. Hosting on Home Assistant

Directory `config/www/higrow/` on HA:

- `firmware.bin` — current build
- `manifest.json` (generated by the deploy target):

```json
{
  "version": "5.4.0",
  "file": "firmware.bin",
  "md5": "<md5-hex>",
  "size": 1184384
}
```

HA serves `config/www` at `https://<ha-ip>:8123/local/higrow/…` without
authentication — the ESP32 only needs HTTP GET, no token. The base URL is
configured as `otaBaseUrl` in `user-variables.h` (empty = OTA disabled); the
variable is documented in the `RENAME TO user-variables.h` template.

**SSL:** This HA instance serves port 8123 via HTTPS only (plain HTTP returns
an empty reply). If `otaBaseUrl` starts with `https`, the ESP32 uses
`WiFiClientSecure` with `setInsecure()` — no certificate validation on the
local network; firmware integrity is ensured by the MD5 check from the
manifest.

### 2. Update logic on the sensor (`src/ota-update.h`)

`checkForOtaUpdate(rel)` is called in `setup()` immediately after
`connectToNetwork()`. The logic is split into three functions:

- `otaParseManifest()` — parses the manifest with ArduinoJson
  (`StaticJsonDocument<256>`); invalid JSON or missing fields ⇒ `false`.
- `otaUpdateRequired()` — version comparison via `!=`; empty manifest version
  ⇒ `false`.
- `checkForOtaUpdate()` — orchestration:

1. HTTP GET `manifest.json` (connect timeout 3 s, read timeout 5 s). Error or
   unreachable ⇒ serial message, function returns, the normal cycle
   continues. OTA is never a blocker.
2. Parse the manifest, compare the version to `rel`; equal ⇒ "up to date",
   back to the normal cycle.
3. On a differing version: stream `firmware.bin` (read timeout 10 s) into the
   inactive OTA slot using the Arduino `Update` library —
   `Update.begin(size)`, `Update.setMD5(md5)`, `Update.writeStream()`.
   Serial progress output in 10% steps.
4. Incomplete download or `Update.end()` failure (also covers MD5 mismatch)
   ⇒ `Update.abort()`, the old slot stays active.
5. Success ⇒ `ESP.restart()`. The reboot starts the new firmware, which then
   handles measurement, MQTT publish (including the new `rel` via the
   existing release sensor) and deep sleep.

SPIFFS is untouched by OTA (only the app partition is swapped);
`/name.conf`, `/soil.conf`, `/batinfo.conf` are preserved.

All serial output is prefixed with `[OTA]` (matching the `[NTP]` style).

### 3. Partition scheme

OTA needs two app slots. The default scheme of `esp32dev` (`default.csv`) has
2 × 1,310,720-byte app slots — it remains in use unchanged. The 5.4.0 build
occupies 1,176,845 bytes (89.8% of the slot; HTTPClient pulls in mbedTLS,
which costs ~180 KB compared to 5.3.0), leaving ~130 KB of headroom. If the
build ever outgrows the slot limit, the way out is
`board_build.partitions = min_spiffs.csv` (2 × ~1.9 MB app) — that wipes the
SPIFFS content once, and all devices need a USB flash plus re-setting the
plant name and calibration.

**Migration to 5.4.0:** One last USB flash of all devices
(`pio run -t upload`). Since the partition scheme stays the same,
`/name.conf`, `/soil.conf` and `/batinfo.conf` are preserved. All further
versions arrive over the air.

### 4. Deployment: PlatformIO target `ota_deploy`

In `platformio_extra.py`, analogous to the existing `reset` target. The
target:

1. Builds the firmware (dependency on `$BUILD_DIR/${PROGNAME}.bin`).
2. Reads the version from `src/main.cpp` (`const String rel = "…"`).
3. Computes MD5 and size of `firmware.bin`, writes `manifest.json` into the
   build directory.
4. Copies both via `scp` (Terminal & SSH addon, key-based) to
   `/config/www/higrow/` on HA; the remote directory is created beforehand
   via `ssh mkdir -p`. Target host/port/path are variables (`OTA_HOST`,
   `OTA_PORT`, `OTA_REMOTE_DIR`) at the top of the script.

Copy order: `firmware.bin` first, then `manifest.json` — the manifest never
points to an incomplete binary.

### 5. Operation

- **Roll out a new version:** Increment the version in `src/main.cpp`
  (`const String rel`), then `pio run -t ota_deploy`.
- **Manual alternative:** Copy `firmware.bin` and `manifest.json` from
  `.pio/build/esp32dev/` to `config/www/higrow/` via the Samba share (same
  order: binary first, then manifest).
- **Disable OTA:** Set `otaBaseUrl` in `include/user-variables.h` to empty.
- **Verify:** `curl -k https://192.168.1.6:8123/local/higrow/manifest.json`
  or the release sensor in Home Assistant after the next wake-up.

### 6. Side finding during implementation

The unused `ArduinoHttpClient` dependency was removed: its `HttpClient.h`
shadowed the framework header `HTTPClient.h` on case-insensitive filesystems
(Windows) and broke the build.

## Failure cases

| Case | Behavior |
|---|---|
| Manifest unreachable / invalid JSON | Normal cycle, sleep as usual |
| Download aborts / MD5 mismatch | `Update.abort()`, old slot stays active, retry on next wake-up |
| New firmware boots but crashes | Known limitation: no automatic rollback. Organizational safeguard: test every version on one device via USB first, then put it into the manifest |

## Verification

Checked during implementation (2026-07-11):

- Build successful, flash 89.8% / RAM 16.2%.
- `pio run -t ota_deploy` runs end to end: manifest generated, both files on
  HA via scp, MD5 on HA identical to the manifest.
- `curl -k https://192.168.1.6:8123/local/higrow/manifest.json` returns the
  deployed manifest (version 5.4.0).

Hardware tests on the serial monitor (after the initial USB flash):

1. No manifest reachable ⇒ normal cycle, no hang.
2. Same version ⇒ "up to date", no update.
3. New version ⇒ download progress, reboot, new `rel` in HA.
4. Deliberately wrong MD5 in the manifest ⇒ abort, device keeps running the
   old version.
